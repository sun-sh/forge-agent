# Forge Agent 产品与工程审查

审查范围：0.2.0 活动源码、测试、双语 README、评测和发布脚本。Pi Coding Agent / Pi AI 固定为 1.4.0。这里只评价实现与证据，不把 fixture 或 CI 当作真实模型编码能力。

## 判断

Forge 已具备本机 Web coding agent 的主要产品链路：项目与会话、第三方模型、流式对话、工具执行、验证、停止恢复、MCP、Skills、作用域记忆、子任务、变更审阅和后台运行。它适合本机开发与早期公开反馈。可展示的 Agent 开发能力在任务状态、完成门禁、权限策略、执行所有权、预算、持久化与恢复设计；Pi 负责成熟的模型/工具循环，不另造运行时。

2026-11-08 的系统复审进一步检查了活动源码、真实任务记录和隔离复现。下述修复已针对完成状态、证据有效期、任务路由和规划收敛落地；更大规模任务与连续多 Agent 交付仍需继续验收。费用预算充足；累计 token 达到人为上限只说明该次执行被中止，不能据此判定模型的编码能力或任务最终可完成性。

以下的“已复现”指确定行为，“源码确认”指可直接检查的实现路径，“待实测”指改进方向或证据缺口。没有把建议写成已完成能力。

| 维度 | 已实现 | 证据或限制 |
| --- | --- | --- |
| 完成与失败 | 自适应和显式规划执行、独立上下文审阅、有限修复、原始验证输出、预算、任务恢复 | `src/task/`、`src/verification/`；独立模型审阅仍不是正确性证明。 |
| 结构化交接与终态 | 未确定意图的只读理解、完整约束与验收 ID、逐项审阅、统一收尾服务 | `plan.ts`、`lifecycle.ts`；语义仍可能误解，永久保存故障无法承诺落盘。 |
| 执行追踪与写入 | 从 Pi 日志投影阶段/模型/工具/检查与重试，右侧按需加载；计数合并与索引写量计数 | `timeline.ts`、`registry.ts`；只读投影，不是可任意恢复的动作 DAG，尚无长任务性能收益结论。 |
| 变更恢复 | 工作文件检查点、按文件 diff/撤销、脏基线保留、HEAD/index 与后续修改检查 | `checkpoints.ts`；逐文件日志，没有跨文件原子事务、全局快照回收或备份保证。 |

| 子 Agent | 独立 Pi 上下文、异步启动与结果汇总、受限角色、worktree worker、应用并验证 | `subagents.ts`、`worktrees.ts`；无 shell、自动三方合并、独立子模型或面板续聊。 |
| 模型兼容 | 可选流式文本、工具参数、工具结果回传三步检查 | `providers.ts`；只证明选定接口/模型的探测结果，厂商 OAuth、代理和限流仍需实际验收。 |
| 记忆 | 全局/项目/会话、待审阅候选、目标词项召回、选入诊断、去重和版本冲突 | `memory.ts`；候选未经接受不注入，无向量检索和质量增益结论。 |
| 任务评测 | 固定仓库 commit、外部判题、保护文件、脏工作区、两流程对照、错误完成率、validation gate、fatal report | `evaluate-repository.mjs`；20 题 cohort 已完成 11 题 baseline/reference 校验，真实模型目前只有一题 direct/planned 试运行，尚无大型模型成绩或竞品对照。 |
| 分发 | tarball 文件检查、可执行入口检查、全新安装验证、跨平台 tag 发布流程 | `check-package.mjs`、`release.yml`；配置流程不等于已发布 npm 或桌面安装器。 |

## 本轮修复与剩余边界

- **定向 review 的正确性问题**：陌生表达不再默认 explore；结构化任务理解与用户模式分开，明确实现请求不能静默退化为调研。完整约束和验收在背景之前进入压缩交接。收尾服务统一 direct/planned 的最终结果，封存、模式恢复和保存失败不能仍显示成功。成功 shell 的相同结果也进入重复证据检测。
- **可追踪性与写放大**：只读执行投影保留稳定父子关系、重试与缺失结果语义；用量/进展最多每秒合并一次，关键边界即时保存，索引跳过过期排队快照。回归确认正确性与合并行为，长任务吞吐和误判率仍需测量。独立 reviewer 已接入规划完成门禁；worker 结构化交接与完整生命周期解耦仍需受控实验。
- **完成证据**：UI 分别显示执行、自动验证和模型审阅；direct 不再冒充已审阅，未配置检查不冒充验证通过。评测门禁读取同一个 `isVerified` 判定。
- **版本与失效**：新增独立于 diff 显示上限的工作区指纹、检查命令配置哈希与 freshness。撤销、proposal 应用、终端操作同步失效同项目会话与持久化任务；部分失败也失效。读取与恢复会复核外部变化。原始报告与重试状态保留。
- **路由与记录**：规划模式的用户请求先形成只读结构化理解，再确定执行路径；正则提示只作遥测，不决定跳过实现或改变权限。direct 保留原生 Pi 回合及执行记录，不能通过意图提示绕过证据和待应用提案门禁。聊天框和任务中心继续已停止任务时均保留其原始策略，重启后也不会将自适应任务升级为规划任务；结构化理解本身仍可能出错，需要外部验收。
- **阶段与修复**：inspect/plan 明确结束和交接条件；阻断审阅缺陷可修复后重新验证，与验证失败共享 `verifyRetries`。新增基于实际工具输入/结果的重复观察，先提醒调整策略，仍重复则停止为待处理；时间长本身不触发停滞。验证失败耗尽预算时保存最终变更记录。
- **用量**：记录输入、输出与缓存用量，保留中止后到达的在途 usage；未知价格显示未知。新安装默认执行空间为 90 分钟、240 回合、500 次工具调用、300,000 生成 token，累计请求 token 守卫关闭，费用上限为 40 美元；达到单段上限后可以在原会话中继续。
- **子任务与测试**：存在未处理文件的 worker proposal 阻止实现任务宣称完成，应用后必须重新验证。空提案不阻断。活动测试改为目录自动发现，新测试不再依赖人工登记。
- **Windows 持久化**：验收中观察到检查点清单替换偶发 `EPERM`。宿主元数据替换对 Windows 共享占用类错误最多尝试 6 次，累计等待不超过 620 ms；保留旧目标，永久失败继续报错，项目文件冲突检查保持独立。
- **评测清理**：真实 planned 试运行观察到模型启动的测试进程在预算取消后仍占用 worktree。评测器现在延长有界删除重试并在总循环异常、预算中止或清理失败时写出报告；残留进程仍作为基础设施故障保留，不能算作模型质量结论。

原始撤销案例已用修复后的构建重跑：修改版本通过验证，恢复旧文件后同一断言失败；任务变为 `needs_attention`，历史报告仍为 `passed`，其 freshness 为 `stale`，界面不再显示当前验证通过。这个隔离案例使用本机模拟 Provider，验证的是宿主状态与持久化行为。

版本证据仍是有界内容观察，不是原子快照或环境证明；范围、排除路径和不可确认情况见[使用说明](usage.md)。子任务已支持异步委派和结果汇总，补丁仍采用显式审阅应用流程；自动集成交付、独立子模型、语义检索、统一执行 DAG 和更广泛真实仓库评测仍有缺口。规划流程已有独立 reviewer，但它仍是模型证据，不能把这些修复表述为已经达到行业领先水平。具体取舍与后续验收见 [Architecture Deep Dive](architecture-deep-dive.md)。

## 真实模型验收与纠偏

[结构化交接的中文回归](evaluations/structured-handoff-2026-11-08.md)进一步用未知意图提示验收同一固定仓库。首批 1/2，规划因“调研说明 + 合法 JSON”被旧解析器拒绝而安全停止；修复后单独一批 2/2，规划实际完成所有阶段并逐项确认 11 条验收。原始格式失败与新指纹分开保留，没有误记为成功。额外回归还发现并修复了“应用并验证”的宿主动作误入自然语言路由，以及只读模式结束文案依赖意图的错误。这些修复不改变 Pi 的模型/工具循环。

后续的[真实模型实验与失败分析](evaluations/runtime-depth-2026-11-08.md)公开了五个小任务两流程 10 次执行、固定第三方仓库任务修复后 4 次复跑，以及一次明确委派的双子任务案例。首批仓库结果暴露 Extend 路由遗漏和 TypeScript 环境类型污染；原始四次结果保留，与修复后协议分开报告。新增回归阻止规划流程把扩展请求降成仅验证，并确认 oracle 能隔离环境错误且继续拒绝真实缺陷。这些结果不构成大型仓库或行业性能结论。

最新的[DeepSeek 固定仓库试运行](evaluations/deepseek-swe-multilingual-pilot-2026-11-09.md)记录了一个更严格的外部验收案例：direct 的 visible verification 和 held-out oracle 都通过，但受保护测试文件与锁文件被修改，因此记为 false completion；planned 在执行预算和 Windows 子进程清理边界上失败。该报告只作为协议证据，不能充当 20 题模型结果。

## 系统复审：修复前的原始发现

本节保留原始基线的复现与改进依据；其中的“当前”描述被审查版本，不代表上述修复后的代码状态。

源码基线：`a383ea435f997f264d1214714cfe6ea5ab079544`，Pi 1.4.0。运行证据仅存本机 `.forge-agent/real-evals/2026-11-08/`；本次额外使用独立 home、独立 Git 项目和本机模拟 Provider 做复现，没有调用真实模型或更改用户模型与历史。这些复现验证宿主行为，不计入真实模型成绩。

### P0：显示的完成状态必须与证据一致（已复现）

`src/web/ui/render.js` 的 `sessionOutcome()` 对已完成的 change 任务统一返回“任务完成 · 验证通过 · 已审阅”。这个分支没有检查 workflow、verification 或 review。用 `workflow: direct`、`verification.status: unchecked`、不存在 review 的输入即可复现。

`src/web/server.ts` 的 `finalizeDirectTask()` 允许未配置验证的 change 执行结束为 completed；直接流程也没有强制模型审阅阶段。因此这是一个真实可达的显示错误，不能把已完成一次模型执行说成已经验证并审阅。配置的验证失败仍会阻止完成，这个不变量并未在本次复现中失效。

需要把执行结果、自动验证、模型审阅、尚待应用的补丁分开建模和显示。没有运行的检查显示“未运行”或“未配置”；历史验证说明检查的是哪个版本。Web、任务中心、队列和导出应读取同一份完成证据，避免各自推断。验收至少包括 direct 无验证、有验证无审阅、planned 审阅阻断、停止、预算中止和补丁待应用。

### P0：代码改变后，旧验证不能继续代表当前版本（已复现 / 源码确认）

隔离案例的顺序：模型修改 `sample.txt` → 配置的断言通过 → task 为 completed → 通过 Web 检查点恢复旧内容 → 同一断言立即失败。恢复后 GET 会话仍返回 task completed、verification passed，界面仍显示“验证通过 · 已审阅”，且 review 始终不存在。

确定的缺口位于 `src/web/server.ts` 的 checkpoints POST：应用恢复后直接推送原会话快照，没有使验证证据失效。subagents apply 和独立终端路径也没有相应的失效更新，这是源码确认的同类缺口；本次没有把这两条路径额外算作已运行复现。

验证报告需要绑定项目版本、检查命令配置和执行 ID。Forge 自己的恢复、proposal 应用等写入应立即标记原证据过期；重新检查前不宣称当前代码已通过。外部编辑也需要指纹复核，或者明确显示“此前版本通过，当前版本未确认”。显示用的有界 diff 列表不能独自承担完整版本证明。保留历史结果与原始失败输出，不删除旧证据来掩盖状态变化。

### P1：任务分类仍无法可靠理解多轮意图（已复现）

当前 `src/task/intent.ts` 只分析本条文本。直接调用 `taskKind()` 的结果如下：

| 用户文本 | 当前分类 | 问题 |
| --- | --- | --- |
| 你觉得还有什么需要完善？ | change | 咨询问题被“完善”命中。 |
| 继续 | explore | 没有结合当前任务或已接受计划。 |
| 按刚才的方案处理 | explore | 无法引用上一轮约定。 |
| 修复接口，但不要删除数据库 | explore | 局部保护要求覆盖整个实现意图。 |

影响随流程不同：planned 会根据分类选择只读回答或完整实现；direct 对 answer/explore 不建立任务封套，但 Agent 模式的 Pi 会话仍可使用修改工具。分类并不构成 direct 的权限边界，因此误分类还可能让实际改动缺少完整任务记录。

应把用户选择的能力模式、上下文中的任务引用和具体意图分开处理。正则保留为明显指令的快速提示；上下文解析输出有 schema 的任务目标、验收条件、允许行为和局部保护范围，宿主在用户模式与 Pi 信任边界内执行。分类模型或正则都不能自行扩大权限。验收需要中英混合、先问后做、否定约束、引用代码以及短句续问的多轮案例。

### P1：规划流程缺少阶段退出契约和审阅修复闭环（源码确认 / 真实记录支持）

`TaskController.run()` 对 change 固定执行 inspect、plan、implement、verify、review。每阶段等待一次 Pi 调用结束后才进入下阶段。首次 inspect 传入原始任务和只读阶段说明，没有明确要求交付哪些发现、确认哪些问题后结束；同一 Pi 会话通过 custom messages 继续，阶段间保留此前上下文。verification 失败有有限修复；review 的具体阻断问题会进入 needs_attention，不进入有界的修复及重新验证流程。

真实仓库样例中的 planned 检查阶段约 146 秒，阶段持久化账本记录 30 个模型回合、43 次工具调用；随后才进入 plan 和 implement。最终在累计 token 守卫处中止，未取得 verify/review 结果。两种流程的最后窗口用量分别约为 72k/128k 与 100k/128k，都没有压缩记录；planned 最终约占窗口 78%。这支持检查调研范围和阶段契约，不能证明自动压缩失效、必然循环或模型无法完成。完整记录中仅发现一次完全相同的工具参数调用重复，也不应把所有调研调用统称为重复调用。

改进应保留默认 direct 和用户显式选择 planned 的交互。为 inspect 定义定位结果、关键约束、验收命令与剩余未知；达到条件后交接。以重复读取未变文件、反复相同错误、没有新增证据等信号识别停滞，先改变策略或给出阻塞原因。耗时或调用次数本身不能证明停滞。对有明确验收缺陷的 review 提供有限修复、重新验证和再次审阅，避免让用户重新走完整调研。仍通过 Pi 扩展和会话 API 实现，不另写 agent loop。

### P1：执行守卫与用量统计需要重新校准（源码确认）

`src/task/budget.ts` 的默认累计上限是 750,000 token；`recordUsage()` 只累加 `totalTokens` 和 cost.total，没有分别保存新输入、输出、缓存读取及缓存写入。模型价格缺失或为零时，Web 的预算条仍显示 `$0.00`，而评测报告已能将未知费用表示为 null。

仓库 direct 成功样例累计 1,935,529 token，其中输出 28,272、缓存读取 1,832,768；planned 中止样例累计 3,011,734，其中输出 42,236、缓存读取 2,742,464。这些累计值不是生成量，也不是当前上下文长度，缓存读取本身不证明浪费。费用预算充足时，默认守卫不应让正常复杂任务提前结束后又被解释为模型能力失败。

应独立记录窗口占用、各类用量、执行时间、进展和已知费用；支持适合长任务的明确执行配置，向用户显示终止的真实原因。未知价格显示未知。保留取消、超时和防失控机制，允许在既定授权下给任务足够执行空间。父子并行请求在守卫触发后到达的 usage 仍应被记账；当前 `recordUsage()` 对非 running 状态直接返回，可能漏记已在途的响应，需补回归。

### P1：子 Agent 尚未形成连续交付链路（源码确认）

异步 `start` 已返回句柄，父 Agent 可继续独立工作；`wait/status/result` 管理取回，Pi 结束边界返回未读结果，宿主检查汇总完成。worker 仍没有命令权限，提案需人工选择应用；新增“应用并验证”直接运行主项目检查，无额外模型请求。每次激活仍限制为 3 分钟、12 回合和 120k 累计 token，提高父预算不会自动获得长程 worker。

优先补齐子任务的结构化结果、等待依赖、待应用状态与父任务完成条件。只读探索适合先做异步启动、进度和结果回收；worker 是否增加受限验证，需要与自身权限和工作区策略一起设计。保留默认人工审阅补丁的边界，可提供明确的“应用并验证”操作，恢复父任务时先确认新版本。对同文件冲突、新增文件、测试失败和未应用 proposal 做真实模型案例，再评价多 Agent 是否提高交付率。不能只通过子任务数量证明协作有效。

## 开源实现对照与采用顺序

本次核对的是以下项目的官方材料，不是独立性能排名：

- Pi 以 SDK/RPC 提供模型与工具循环，复杂产品能力放在其上层。本项目保持这个边界。
- OpenCode 将主 Agent、子 Agent 的工具/模型/权限配置放在明确的配置体系中，并区分清理旧工具输出与总结会话的压缩。值得学习的是上下文与能力配置的边界。
- DeepSeek Harness 的生命周期接口区分启动、运行、通知、等待和消息，父任务可在子任务运行期间继续。适合参考 Forge 的异步探索与子会话 UI；不照搬任意委派权限。
- OpenHands SDK 的本地 critic 提供连续卡滞检测与升级后的停滞判断。Forge 需要针对实际无进展迹象改变策略；不能把一次正常的长调试简单截断。
- Anthropic 的长程 harness 实验把实现与评价分开，并通过实际运行和浏览器检查评价交付物。Forge 的模型自审和 configured checks 需要继续与独立验收区分，效果交给固定条件实验判断。

建议按三批验收：

1. **可信完成**：修复 UI 过度声明，绑定并失效验证证据，打通恢复/补丁应用后的状态；补多轮意图案例和活动测试发现。合格标准是界面、API、队列和导出都不把未运行或过期证据当成当前通过。
2. **可靠交付**：明确阶段退出、进展信号与有界审阅修复；拆分用量指标并给长任务合理配置；打通异步探索和 proposal 的待应用、集成、验证状态。每项改变保留单 Agent 对照。
3. **证明质量**：完成陌生仓库重复评测、真实服务兼容矩阵、长程恢复与记忆实验；随后治理历史负载、容量、安装升级和 UI 可维护性。

费用预算充足后，最有价值的投入是更完整的真实任务、失败复现与受控对照。当前报告不把 planned 被累计上限中止当作最终能力失败，也不宣称提高上限就已解决调度问题。

## 值得展示的工程取舍

- **完成门禁与版本绑定**：配置验证失败不能作为成功结束；自动继续不重置修复次数，规划流程检查审阅结果及工作区证据。恢复、补丁应用和终端操作使旧证据失效，界面分别展示执行、验证与审阅状态。
- **副作用有所有权**：同一真实项目的 Agent、终端、Trust 变更、撤销与 proposal 应用共享执行租约。服务关闭先停止准入，再等待打开会话、活跃执行和清理。
- **持久化先于可见成功**：队列落盘后准入，公开快照来自已提交状态，避免界面显示完成而重启后还看到运行中。损坏队列保留原文件并拒绝静默重建。
- **恢复不重放工具**：执行进程退出后标记中断；用户明确继续或重排时先读当前项目状态。未封存或写入中断的检查点不会自动恢复。
- **原有工作有基线**：检查点记录执行前脏内容，撤销不 reset Git；worker 在隔离目录提出补丁，主项目有后续改动时拒绝覆盖。
- **会话归属有边界**：普通 fork 不继承原会话的子任务、检查点或待审阅记忆所有权。UI 的晚到响应和旧按钮也检查当前会话。
- **复用覆盖运行时**：Pi 负责 agent loop、模型、认证、会话树、压缩、内置工具、MCP、Skills、扩展和发现。Forge 控制宿主策略和产品流程，不复制第二套协议或模型循环。

## 已有回归覆盖的失效路径

会话启动期间的加载纳入 shutdown 等待，避免关闭后晚到的 Agent 重新挂回网关。准备阶段失败会释放项目占用并恢复空闲；收尾失败保存失败状态并释放租约。Provider 更新无法重绑定时退休真实 Agent，历史置为只读；删除提交后目录刷新失败不会复活已删除凭据。空闲子会话 abort 或重复 dispose 的尽力清理错误不会篡改已完成结果。

可写子任务还拒绝 Pi 会展开的特殊路径表示，以及父目录链接、硬链接、敏感路径和 Windows 路径别名，确保检查目标与实际写入语义一致。这些是应用控制，不是 OS 沙箱；可信扩展、普通 Agent 工具和验证命令仍拥有启动者权限。
