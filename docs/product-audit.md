# Forge Agent 产品与工程审查

审查日期：2026-11-06。范围：当前活动源码、测试、评测脚本、中英文 README，以及浏览器验收脚本。未调用真实模型，也没有把本地模拟模型的结果当成编码质量或行业排名。

## 结论

Forge 已经具备一个可以展示 Agent 工程能力的 0.1.0 产品骨架：Pi 负责成熟的模型/工具循环、会话树、压缩和资源发现，Forge 负责 Web 产品、执行策略、任务状态、验证门禁、项目互斥、预算和恢复。贡献点在控制边界和失效路径，而不是重新实现一个 agent loop。

当前适合本机开发和早期反馈。它已经覆盖单 home owner、同项目执行互斥、执行预算、作用域记忆隔离和可重跑的五任务评测链路；真实仓库的模型效果、外部服务兼容性、后台任务队列和分发体验仍需要证据，不能仅凭功能数量、CI 或模拟模型通过推断“行业领先”。

| 维度 | 判断 | 依据 |
| --- | --- | --- |
| 职责边界 | 清楚 | Pi 管运行时、会话、资源和 MCP；Forge 管任务、策略、验证、预算、Web 与本机生命周期。 |
| Agent 工程 | 有实质实现 | 规划控制器、有限修复、原始验证输出、只读工具策略、停止、持久化任务和重新检查。 |
| 执行可靠性 | 已补齐核心边界 | 一个 home 只能有一个 Web owner；Agent、终端、Trust 变更共享规范化项目锁；关闭会取消并等待占用释放。 |
| 成本与失控保护 | 已有宿主预算 | 每次执行限制时长、模型回合、工具调用、token 和费用，并记录 `budget_exceeded`。Provider 用量在响应结束时可见，因此仍不是账单级硬隔离。 |
| 记忆与上下文 | 作用域参考资料 | 全局、项目、会话三层可管理；项目记忆按真实目录隔离，Pi 负责自动压缩；自动提取和检索收益尚无证据。 |
| 编码质量 | 尚无法评价 | 五个公开小任务可检查链路，其中两个是跨文件任务；没有已发布的复杂真实仓库 direct/planned 对照。 |
| 产品交付 | 早期版本 | Web 是主入口，源码安装和中文界面；尚无独立后台队列、桌面安装包、npm 发布包和完整外部 Provider 矩阵。 |

## 已实现且值得展示的设计

- **完成由证据控制**：[任务控制器](../src/task/controller.ts) 要求配置验证通过、结构化审阅有效，并检查可用 Git 证据中的审阅期间变更。模型声称完成不会单独改变任务状态。
- **失败不能伪装成功**：[验证扩展](../src/verification/pi-extension.ts) 与 [命令执行器](../src/tools/command.ts) 处理超时、启动失败、取消、原始输出和有限修复次数；内部继续不会重置任务预算。
- **项目操作有统一所有权**：[项目执行占用](../src/web/executions.ts) 使用真实目录身份，把 Agent、终端、Trust 变更和关闭纳入一个生命周期。检查与获取之间没有裸的时间窗口，目录别名不能绕过占用。
- **home 级服务有明确 owner**：[任务索引](../src/task/registry.ts) 使用跨进程租约。第二个 Web 实例会被拒绝并显示不含 token 的本机地址；崩溃后的 stale lease 可以恢复，索引写入失败会出现在任务 API 诊断中。
- **预算进入运行时**：[预算运行时](../src/task/budget.ts) 通过 Pi 的公开事件统计回合、工具、响应 usage 和时限，超过阈值后中止 Pi，任务保留可恢复状态。
- **记忆不会跨项目串用**：[作用域记忆](../src/web/memory.ts) 使用 canonical realpath 与平台目录规则；旧项目文件只有在存储的 scope 与当前项目一致时才迁移，冲突会拒绝注入。
- **恢复先重新检查**：服务重启或预算耗尽后的继续会从当前工作区重新调研，不自动重放旧工具副作用。
- **安全边界进入执行路径**：[模式策略](../src/web/modes.ts) 限制实际工具调用，包括动态和嵌套工具，而不是只隐藏按钮。文件引用还会再次检查真实路径、敏感目录、符号链接和大小。

模型审阅仍然是同一 Pi 会话里的额外模型回合，不构成独立评审或正确性证明。规划、审阅和记忆是否带来净收益，需要用同模型、同任务和固定配置做对照。

## 仍需优先验证的事项

### P1：真实仓库效果

当前评测脚本已经记录 Git revision、suite fingerprint、Pi/Node 环境、workflow、重复次数、p50/p95 latency、token、费用、工具调用、修复和工作区完整性。五个公开任务覆盖边界处理、严格端口、稳定去重和两个跨文件小模块，适合验证工具链与评测门禁。

它们仍然不是 SWE-bench 级别或复杂仓库基准。下一步应该增加公开、可固定 revision 的真实仓库任务，覆盖 bug 修复、功能实现、重构、上下文压力、中断恢复和已有脏改动；用 `--workflow both --repeat N` 做 direct/planned 对照，保留失败样例和错误完成率。没有这组结果前，README 只应说明评测基础设施可运行。

### P1：外部服务兼容矩阵

本机浏览器验收使用本地模拟 OpenAI-compatible 服务，验证 Web、Pi 和 UI 链路。Provider 编辑器覆盖 OpenAI Chat Completions、OpenAI Responses 和 Anthropic Messages 的常用配置；OAuth、企业代理、限流、流式差异、模型能力字段和非标准错误仍需按真实服务验收。MCP 已有本地 OAuth fixture，但不能替代厂商级兼容测试。

### P2：后台运行与终端协议

同一网关内的会话可以在浏览器标签离开后继续，任务索引也能恢复；产品还没有独立队列、跨网关 worker、终端运行 ID 或终端面板中的取消按钮。现在的终端 API 是一次 HTTP 请求，关闭服务会通过共享 AbortSignal 取消并等待命令释放项目锁。若要扩展到长任务，应先设计任务 owner、事件游标、取消确认、输出保留和退出状态，再引入队列。

### P2：记忆质量与上下文选择

现在的三层记忆是用户维护的参考资料，按作用域注入并受字符上限约束；Pi 负责会话压缩和历史树。自动经验提取、向量检索、冲突处理、时效和 token 预算尚未实现，也没有证明它们会提升编码结果。应先用可审查的记忆检索实验测量增益，再决定是否加入自动学习。

### P2：交付与可维护性

Web gateway 和主 UI 仍然偏集中，后续可以按会话生命周期、项目执行、设置路由和视图状态拆分。当前安装是源码方式，缺少 npm release、桌面安装包、升级/回滚和跨平台发布矩阵。这个顺序应排在可靠性和真实效果证据之后，不需要为了换 UI 框架重写运行时。

## README 审查

首页现在按“产品用途 → 快速启动 → 工作区能力 → 模式与流程 → Forge/Pi 职责 → 验证与评测 → 边界与安全”的顺序组织。预算、home owner、项目互斥、五任务评测和真实模型限制已经写入；按日期罗列的测试数量和 CI 成绩不放在产品介绍中。详细的 `/` 命令、Skills、MCP、记忆和本机数据放在双语使用指南。

面向 Agent 开发岗，项目介绍应重点讲清三个问题：为什么复用成熟 runtime、Forge 自己控制哪些宿主级边界、失败时如何恢复并留下证据。复用 Pi 是明确的工程取舍；可展示的原创能力是任务状态与完成门禁、工具策略、执行所有权、预算和 Web 交互的组合设计。

## 发布判断

可以作为公开的 0.1.0 工程项目继续迭代和收集反馈。发布说明应写成“本机 Web coding agent，基于 Pi runtime，新增任务编排、验证、预算和恢复控制”，并明确真实模型质量仍未发布。下一次版本优先补真实仓库对照、Provider/MCP 兼容和故障诊断；在此之前不要声称与 Codex、Claude Code 或其他成熟产品的编码效果等价。
